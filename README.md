# COMPASS — Mental Health Chatbot Backend

COMPASS is the "brain" behind a mental health support chatbot. You type how you feel, and it:

1. **Understands the emotion** behind your message using a trained AI model (anger, anxiety,
   confusion, sadness, or neutral).
2. **Replies with empathy** — a warm, supportive message using CBT (Cognitive Behavioural
   Therapy) techniques, generated by a large language model.
3. **Watches for danger.** If a message suggests self-harm or suicide, it skips the AI and
   responds with a fixed, carefully-worded safety message containing **Nigerian crisis
   hotlines** — and can **email a real therapist** so a human follows up.
4. **Speaks three languages** — English, Yoruba, and Nigerian Pidgin.

It is a **backend** (an API + a small built-in chat web page). A separate website (the
"frontend") or a mobile app talks to it over the internet.

# Part 1 — Run It Yourself (No Experience Needed)

This section assumes **zero programming experience**. Follow it top to bottom. You will type a
few commands into a "terminal" — a text window where you tell the computer what to do. Don't
worry, every command is given to you exactly.

> **How long will this take?** About 15–25 minutes, most of it waiting for downloads.
> **Will it cost money?** No. Everything used here has a free tier.

### What the service needs (and what's optional)

| Thing | Needed? | If you skip it |
|-------|---------|----------------|
| Python 3.12 | **Required** | Nothing runs |
| The AI model (auto-downloaded) | **Required** | Emotion detection won't load |
| A Groq API key (free) | **Strongly recommended** | Replies fall back to fixed templates (still works, less natural) |
| Redis | Optional | The app uses its own memory instead; fully works |
| MongoDB | Optional | Conversations just aren't saved to a database |
| Email (SMTP) settings | Optional | Therapist alert emails are turned off |

## Step 0 — Install the two tools you need

You need **Python** (the language the project is written in) and **Git** (to download the

- **Windows:** press the Start button, type `PowerShell`, press Enter.

```powershell
git --version
```

"python is not recognized", you missed the "Add to PATH" checkbox — re-run the Python

# Part 2 — How It Works

### The request pipeline

Every message flows through one pipeline (`services/nlp_pipeline.py`). Each stage does exactly
one job, which keeps the code easy to follow, test, and reason about:

```
User message
    │
    ▼
1. InputValidator   reject empty / too-long input, strip HTML & control chars   (middleware/)
    │
    ▼
2. RateLimiter      block abuse via a Redis counter (fails open if Redis is down) (middleware/)
    │
    ▼
3. LanguageService  detect en / yo / pcm; translate non-English input to English  (services/)
    │
    ▼
4. Preprocessor     strip URLs, collapse "soooo" → "sooo", normalise whitespace   (services/)
    │
    ▼
5. EmotionClassifier DistilBERT (ONNX) → emotion label + confidence               (models/)
    │
    ▼
6. DialogueManager  update session state, detect crisis, choose reply strategy    (services/)
    │
    ├── crisis?  ──► fixed safe template + Nigerian hotlines  +  email a therapist
    │                (never sent to the LLM)
    │
    └── otherwise ► Groq LLM empathetic reply, with a CBT template fallback        (services/)
    │
    ▼
7. LanguageService  translate the reply back to the user's language               (services/)
    │
    ▼
8. MongoDB (optional) persist the conversation record                             (app.py)
    │
    ▼
JSON response → { reply, emotion, confidence, language, session_id }
```

### Two safety rules

- **Crisis is never delegated to the LLM.** If a message trips the crisis layer, the reply
  comes from a fixed, localized template so the emergency wording and hotline numbers stay
  exact. This decision happens *before* the LLM is ever called. A crisis turn also escalates to
  a human — see [Therapist escalation](#8-therapist-escalation-servicesalert_servicepy).
- **The app degrades gracefully.** Redis, MongoDB, and the Groq LLM are all optional. If Redis
  is down, the app uses an in-process cache and stops rate-limiting (fails *open* — users are
  never wrongly blocked). If MongoDB is down, it skips persistence. If Groq is unavailable, it
  falls back to built-in CBT templates. The chatbot keeps answering in every case.

# Part 3 — Implementation Details

This section explains *how* each component actually works, not just what it does. File paths are
given so you can read along.

## 1. Input validation (`middleware/input_validator.py`)

`validate_input()` runs before anything touches the model, in this order:

1. **Type check** — must be a string, else `InputValidationError`.
2. **Length check first** — rejects anything over `MAX_RAW_CHARS` (default 1000) *before*
   sanitizing, so a huge malicious payload is dropped cheaply.
3. **Unicode NFKC normalization** — collapses look-alike characters (e.g. full-width "Ａ" → "A").
4. **HTML stripping** — removes `<...>` tags via a precompiled regex (basic XSS defense).
5. **Control-character stripping** — removes null bytes and control chars, but keeps `\t \n \r`.
6. **Whitespace normalization**, then an **empty check last** — so input that was *only* HTML
   (e.g. `<script></script>`) is correctly rejected as empty.

Errors carry user-safe messages that routes can return directly as `400`s. Regexes are compiled
once at import for speed.

## 2. Rate limiting (`middleware/rate_limiter.py`)

A **fixed-window counter** in Redis. For each user the key `rate:{user_id}` is incremented and
given a TTL equal to `RATE_LIMIT_WINDOW_SECONDS` (default 60). `INCR` and `EXPIRE` are sent in a
single Redis **pipeline** (one round-trip). If the count exceeds `RATE_LIMIT_REQUESTS` (default
30), a `RateLimitError` → `429` is raised.

Redis is shared across all Gunicorn workers, so the limit is global, not per-worker (a key
reason this isn't done with in-memory Flask-Limiter). **If Redis is down, it fails open** — the
error is logged and the user is allowed through, because blocking real users is worse than
briefly losing rate-limiting.

## 3. Language detection & translation (`services/language_service.py`)

- **Detection** is deliberately lightweight: an explicit `language` hint from the request wins;
  otherwise the text is scanned for curated Yoruba and Pidgin marker phrases, and the higher
  score wins (defaulting to English). It returns a `(language, confidence)` tuple. The function
  is isolated so a heavier ML detector can replace it later without touching the pipeline.
- **Translation** goes through a `TranslationProvider` protocol. The default `groq` provider
  sends a careful translator prompt (preserving hotline numbers, names, line breaks) with
  per-language style notes that pin down natural phrasings. If no provider is configured, a
  `NoopTranslationProvider` passes English through and refuses other languages.
- **Crisis safety:** crisis replies for Yoruba/Pidgin use **fixed localized templates**
  (`_LOCALIZED_CRISIS_REPLIES`), never live machine translation — so emergency wording and
  hotline numbers can't be distorted. Crisis is also detected directly in Yoruba/Pidgin via
  language-specific marker lists, independent of the English classifier.

The flow is **translate-in / translate-out**: non-English input is translated to English for the
classifier, and the English reply is translated back to the user's `reply_language`.

## 4. Preprocessing (`services/preprocessor.py`)

A stateless cleanup pass (no model, no I/O) applied to the English text before tokenization:
strip whitespace → remove URLs → collapse runs of the same character to 3 (`"sooooo"` → `"sooo"`,
which preserves emphasis without wasting tokens) → normalize whitespace → hard-cap length. It's
fast enough to be negligible in the latency budget.

## 5. Emotion classification (`models/emotion_classifier.py`)

The classifier is loaded **once** at startup as a module-level singleton and shared by all
requests. Key details:

- **ONNX Runtime by default.** The fine-tuned DistilBERT is exported and INT8-quantized to ONNX
  (~2–4× faster on CPU than PyTorch, ~67 MB). If ONNX fails to load, it **automatically falls
  back to PyTorch**, applying dynamic INT8 quantization there too. Thread count is capped
  (`intra_op_num_threads = 2`) to avoid oversubscription on short inputs.
- **Tokenization** pads/truncates to `max_length=128`. Attention is O(n²) in length, so 128 vs
  512 is ~16× less attention compute, and 128 tokens covers virtually all chat messages.
- **Two-layer caching.** (a) A process-local `@lru_cache(256)` on the raw inference function
  makes repeated messages instant even with no Redis. (b) An optional Redis cache keyed on
  `pred:{sha256(text)[:16]}` with a short TTL (`PREDICTION_CACHE_TTL`, default 60s) shares
  results across workers. Cache writes are best-effort and never block a response.
- **Confidence gating.** Logits → softmax → top class. If the top probability is below
  `CONFIDENCE_THRESHOLD` (default 0.50) the emotion becomes `uncertain`, and the bot asks a
  gentle clarifying question instead of guessing.
- **Warmup.** One dummy inference runs at startup so the first real user request isn't slow.

## 6. Dialogue manager (`services/dialogue_manager.py`)

A small **state machine** whose state lives in Redis as JSON under `session:{user_id}` with a
TTL (`SESSION_TTL_SECONDS`, default 30 min). The class itself is stateless and safe to share.

- **`update_state()`** records the latest emotion/message/turn count and — critically —
  **runs crisis detection here** so `crisis_flag` is set *before* the pipeline decides whether
  to call the LLM. (Crisis detection: the model can't emit a "suicidal" label, so this relies on
  a curated phrase list, `_CRISIS_KEYWORDS`, covering suicidal intent, inability to continue,
  and self-harm.)
- **`get_next_reply()`** picks a reply by priority: **crisis** (hotline template, cancels any
  active exercise) → **greeting** → **active CBT flow** (next step) → **uncertain** (clarify) →
  **emotional response + a CBT offer**.
- **CBT flows** (`breathing`, `journaling`, `grounding`) are step-by-step scripts. When a user
  agrees ("yes", "ok", …) to an offer, the flow activates and advances one step per turn.
- **spaCy** extracts light entities (e.g. a duration like "for two weeks") to make replies feel
  more specific. If the spaCy model isn't installed, this degrades to no entities.

## 7. LLM reply generation (`services/llm_service.py`)

For non-crisis turns, `generate_reply()` calls Groq (Llama 3, configurable via `GROQ_MODEL`).
It builds: a strict mental-health **system prompt** (the "Mira" persona, with hard safety rules:
never diagnose, never claim to be human, defer crises), the last `LLM_HISTORY_TURNS` messages
for context, and the current message **annotated** with the detected emotion + a per-emotion tone
guidance line. It uses `LLM_MAX_TOKENS`, `temperature=0.75`, and a timeout of
`LLM_TIMEOUT_SECONDS`. Any failure (no key, network, timeout) raises `LLMUnavailable`, and the
pipeline silently falls back to the dialogue manager's templates — the user always gets a reply.

## 8. Therapist escalation (`services/alert_service.py`)

When the pipeline confirms a **hard crisis**, it calls `maybe_alert_therapist()` to email an
on-call therapist while the user simultaneously receives the crisis template. It is engineered to
be safe by construction:

- **Fail-safe.** The SMTP send runs on a **background daemon thread** and every error is
  swallowed and logged. Alerting can never delay, alter, or break the user's crisis reply.
- **De-duplicated.** At most **one alert per user per `ALERT_COOLDOWN_SECONDS`** (default 15
  min), so an ongoing crisis conversation doesn't flood the therapist. The cooldown uses a Redis
  `SET key value NX EX` (atomic, shared across workers); if Redis is down it falls back to an
  in-process timestamp map.
- **Opt-in.** Does nothing unless `ENABLE_THERAPIST_ALERTS=true` **and** a recipient + `SMTP_HOST`
  are configured. With it off, behavior is identical to before.
- **Transport** is plain SMTP via Python's standard library (no extra dependency). Port 465 uses
  implicit TLS; otherwise STARTTLS is used. This works with Gmail, SendGrid's SMTP relay,
  Mailgun, etc.

The email contains the session ID, timestamp, detected emotion + confidence, what triggered the
crisis, the user's message, and (for non-English) the English translation.

**Enabling alerts** — add to `.env`:

```env
ENABLE_THERAPIST_ALERTS=true
THERAPIST_ALERT_EMAIL=oncall-therapist@example.com
ALERT_EMAIL_FROM=alerts@yourdomain.com        # defaults to SMTP_USERNAME
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USERNAME=you@gmail.com
SMTP_PASSWORD=your-app-password               # Gmail "app password", not your login password
SMTP_USE_TLS=true
ALERT_COOLDOWN_SECONDS=900
```

> **Privacy note:** an alert forwards the user's message to the configured therapist. That is
> appropriate and necessary for an emergency follow-up, but the recipient must be a real,
> authorized clinician and the channel one you trust.

## 9. Persistence & logging

- **MongoDB (optional).** `app.py` connects with a short timeout and creates indexes on first
  connect. Each turn is written by `nlp_pipeline._log_to_mongo()` as a record (user, message,
  emotion, confidence, reply, latency, language metadata). Failures are logged, never fatal.
- **Structured logging (`utils/logger.py`).** Every log line is a single JSON object on stdout
  (so Gunicorn/Docker/Datadog can parse it). Dedicated events: `prediction`, `http_request`,
  `error`, `session`, and `crisis_detected` (logged at CRITICAL). Message text is **not** logged
  — only its length — for privacy.
- **Redis connection pool (`utils/redis_pool.py`).** One shared pool with deliberately short
  (0.5s) connect/read timeouts so that when Redis is unavailable the app fails open *fast*
  instead of hanging each request.

# Part 4 — The Emotion Model

A DistilBERT model fine-tuned on mental-health conversational data. It predicts **five
emotions**: `anger`, `anxiety`, `confusion`, `neutral`, `sadness` (see `label_classes.json`).

> **Note:** "suicidal" and "depression" are *not* model classes. Suicidal-risk detection is
> handled by the keyword / language-marker crisis layer
> ([§6](#6-dialogue-manager-servicesdialogue_managerpy) and
> [§3](#3-language-detection--translation-serviceslanguage_servicepy)), which is more reliable
> for safety-critical wording than a learned label.

### Validation performance

Best epoch macro-F1 **0.9368** across **708** validation instances:

| Emotion     | Precision | Recall | F1-Score | Support |
|-------------|-----------|--------|----------|---------|
| `anger`     | 0.9655    | 0.9333 | 0.9492   | 150     |
| `anxiety`   | 0.8947    | 0.9067 | 0.9007   | 150     |
| `confusion` | 0.8992    | 0.9907 | 0.9427   | 108     |
| `neutral`   | 0.9603    | 0.9667 | 0.9635   | 150     |
| `sadness`   | 0.9574    | 0.9000 | 0.9278   | 150     |
| **accuracy**    |        |        | **0.9364** | 708 |
| **macro avg**   | 0.9354 | 0.9395 | 0.9368 | 708    |

The training/eval scripts are `train.py` (fine-tune), `download_dataset.py` (data),
`convert_to_onnx.py` (export + quantize), and `upload_model.py` (publish to HuggingFace). The
full report is in `training_report.txt`.

# Part 5 — API Reference

| Method | Route       | Description                                          |
|--------|-------------|------------------------------------------------------|
| GET    | `/`         | Built-in chat UI                                     |
| POST   | `/send`     | Send a message → `{ reply, emotion, confidence, ... }` |
| POST   | `/webhook`  | Dialogflow fulfillment webhook                       |
| GET    | `/health`   | Health check (Redis + model + Mongo status)          |

### `POST /send`

Request body (only `message` is required):

| Field                | Values                    | Purpose                                          |
|----------------------|---------------------------|--------------------------------------------------|
| `message`            | string                    | The user's message (**required**)                |
| `session_id`         | string                    | Stable conversation ID from the frontend         |
| `conversation_id`    | string                    | Alias for `session_id`                           |
| `language`           | `auto`, `en`, `yo`, `pcm` | Input language hint                              |
| `preferred_language` | `auto`, `en`, `yo`, `pcm` | Backward-compatible alias for `language`         |
| `reply_language`     | `en`, `yo`, `pcm`         | Force the bot reply language                      |

Example:

```bash
curl -X POST http://localhost:5000/send \
  -H "Content-Type: application/json" \
  -d '{"message": "I feel really anxious and cannot sleep", "language": "auto"}'
```

Response:

```json
{
  "reply": "It sounds like you're feeling overwhelmed with anxiety right now. 💙 ...",
  "emotion": "anxiety",
  "confidence": 0.9888,
  "session_id": "compass-conversation-id",
  "language": {
    "detected": "en",
    "reply": "en",
    "provider": "groq",
    "input_translation_applied": false,
    "output_translation_applied": false
  }
}
```

Status codes: `200` success · `400` invalid input · `429` rate-limited · `500` internal error.

# Part 6 — Configuration Reference

All configuration is read from environment variables (`config/settings.py`). Copy `.env.example`
to `.env` and edit. Most relevant settings:

| Variable                          | Default                        | Purpose                                            |
|-----------------------------------|--------------------------------|----------------------------------------------------|
| `FLASK_ENV`                       | `production`                   | `development` enables the auto-reloading debug server |
| `PORT`                            | `5000`                         | Port the server listens on                          |
| `SECRET_KEY`                      | `change-me-...`                | Flask session signing — set a random value          |
| `FRONTEND_ORIGINS`                | localhost + Vercel URLs        | Comma-separated allowed CORS origins                |
| `GROQ_API_KEY`                    | —                              | Groq key for LLM replies + translation              |
| `GROQ_MODEL`                      | `llama-3.1-8b-instant`         | Groq model name                                     |
| `USE_ONNX`                        | `true`                         | Use the fast ONNX runtime (falls back to PyTorch)   |
| `MODEL_DIR` / `ONNX_MODEL_PATH`   | `./distilbert_finetuned` / …   | Where the model + ONNX export live                  |
| `CONFIDENCE_THRESHOLD`            | `0.50`                         | Below this, emotion is returned as `uncertain`      |
| `ENABLE_MULTILINGUAL`             | `true`                         | Enables language detection + translation            |
| `SUPPORTED_LANGUAGES`             | `en,yo,pcm`                    | Enabled language codes                              |
| `LLM_HISTORY_TURNS`               | `6`                            | Recent messages sent to the LLM for context         |
| `LLM_TIMEOUT_SECONDS`             | `8.0`                          | LLM timeout before template fallback                |
| `RATE_LIMIT_REQUESTS` / `_WINDOW_SECONDS` | `30` / `60`            | Per-user rate limit                                 |
| `SESSION_TTL_SECONDS`             | `1800`                         | How long a conversation's session state lives       |
| `ENABLE_THERAPIST_ALERTS`         | `false`                        | Master switch for emergency therapist email alerts  |
| `THERAPIST_ALERT_EMAIL`           | —                              | On-call therapist recipient address                 |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USERNAME` / `SMTP_PASSWORD` | — / `587` / — / — | SMTP transport for alerts        |
| `ALERT_COOLDOWN_SECONDS`          | `900`                          | Max one therapist alert per user per window         |

### Infrastructure

| Service | Purpose                                        | Required? | Default            |
|---------|------------------------------------------------|-----------|--------------------|
| Redis   | Session state, prediction cache, rate limiting | Optional  | `localhost:6379`   |
| MongoDB | Conversation persistence                       | Optional  | `localhost:27017`  |
| Groq    | LLM replies + translation                      | Optional* | —                  |
| SMTP    | Therapist emergency alert emails               | Optional  | —                  |

\* Without Groq the bot still works using built-in CBT templates (English only).

> **Local-dev gotchas:** `config/settings.py` defaults `PORT` to `5000`, but a *deployed* `.env`
> may set `10000`. Likewise a deployed `.env`'s `REDIS_URL` / `MONGO_URI` point at cloud hosts
> that aren't reachable from your laptop — use local values (or leave them) for local runs.

# Part 7 — Testing

All tests are self-contained — heavy dependencies (torch, redis, spacy, onnxruntime, pymongo)
are **mocked**, so no model, key, or Redis instance is required.

```powershell
python -m unittest tests/test_nlp_pipeline.py -v
```

There are **48 tests** covering input validation, preprocessing, rate limiting, the dialogue
manager (including crisis routing and the expanded keyword list), the language service, the LLM
service, the `/send` endpoint, and the therapist alert service.

`pytest` is not a project dependency, but the tests are pytest-compatible if you prefer it
(`pip install pytest && pytest tests/ -v`).

**Live language acceptance** (calls the real translation provider — needs `GROQ_API_KEY`):

```powershell
python scripts/check_language_acceptance.py
```

See `docs/language_acceptance.md` for the manual Yoruba/Pidgin review checklist and
`docs/frontend_integration.md` for the frontend request/response contract.

# Part 8 — Deployment

For production use a real WSGI server instead of `python app.py`:

```bash
gunicorn app:app --bind 0.0.0.0:$PORT --workers 1 --timeout 120 --preload
```

`render.yaml` is a ready-to-use [Render](https://render.com) blueprint: it defines the web
service plus a managed Redis instance, and runs `startup.py` during the build to download the
model from HuggingFace. Secrets (`GROQ_API_KEY`, `HF_TOKEN`, `MONGO_URI`, and SMTP values) are
set in the Render dashboard, not committed.
